# 本地智能调度算法理论方案

调研日期：2026-09-25。本文针对三个目标：区间动态限速、客货在并行线路间分配、列车进站时的站台与进路选择。它讨论算法与数据契约，不表示相关控制已经在游戏中启用或完成实机安全验收。

对应的可执行任务清单见 [智能调度算法 TODO](../agents/INTELLIGENT_DISPATCH_ALGORITHM_TODO.md)。

## 1. 推荐的总体结构

不建议使用一个同时决定每辆车速度、每名旅客线路和每条站内进路的单体模型。这会形成带车辆动力学、离散进路选择和多商品流量的混合整数非线性问题；求解时间、数据完整性和现有执行器粒度都不适合在线控制。

推荐采用分层滚动时域控制：

1. **安全与速度监督层**：高频更新列车有向位置、前车、可用间隔和速度上限。它只能收紧上层计划，不能为追赶运行图而放宽安全边界。
2. **站场资源调度层**：在数分钟预测窗内联合选择进路、站台、列车先后次序和预计占用时段，只执行最靠近当前时刻且尚未锁定的一步。
3. **客货分配层**：按有向 OD、具体车次和线路区段剩余容量，在较低频率上调整尚未上车的客货分配。
4. **共享协调层**：维护轨道区段、咽喉、站台和车次容量的时间预约表。站场调度产生未来延误与拥堵价格，客货分配用它减少向拥堵线路导流；客货预测反过来改变停车时间和站场调度成本。
5. **执行与验证层**：所有输出都转换成有期限、可撤销、可归因的命令。每个周期只提交近期动作，再用下一帧实际状态验证。

这属于铁路实时交通管理常见的“状态估计—预测—冲突消解—速度调节—滚动执行”结构。实时铁路交通管理研究也把冲突消解和速度调节作为相互连接但可分解的模块，而不是单一规则。[D'Ariano、Pacciarelli 与 Pranzo，2007](https://doi.org/10.1016/j.trb.2006.02.005)

## 2. 统一状态与资源模型

### 2.1 有向资源图

将路网表示为有向资源图。资源至少包含：

- 普通区间边与信号闭塞；
- 道岔和互相冲突的进路组；
- 站台轨及其有效长度；
- 站前等待点；
- 线路的有向停站序列；
- 具体车次在各区段的可用容量。

每个资源记录 `[最早进入时刻, 预计释放时刻, 占用列车, 置信度]`。如果方向、长度、释放时刻或列车位置不可信，该资源不得进入自动执行集合。

### 2.2 列车状态

列车 `i` 的最小状态为：

`x_i = (directed_path, s_i, v_i, length_i, line_i, next_stop_i, locked_i, freshness_i)`

其中 `s_i` 必须是实际有向路径上的累计距离，不应使用无向最短路或仅按节点直线距离估算。位置误差、采样延迟和车长误差作为显式不确定量进入安全余量。

### 2.3 需求状态

需求按 `(entity_kind, cargo_id, origin, destination, time_bucket)` 分组。乘客和每种货物分别建账，不合并 A→B 与 B→A。每组同时记录：

- 当前候车数与已经在车数量；
- 可用线路和各线路的有向站序；
- 接下来若干具体车次的到达时刻与逐区段剩余容量；
- 数据是否截断、未知或采集失败；
- 上一周期分配结果和冷却时间。

## 3. 目标一：基于前车间隔的区间限速

### 3.1 算法选择

采用**安全速度包络加滚动预测控制**。游戏信号系统继续负责合法进路和基础防撞，本算法作为上层速度监督器，用更早、更平滑的限速减少追停和排队。ETCS 的理论也是同时监督静态速度曲线和动态速度曲线，并在达到干预曲线前给出预警；实际制动由车辆制动系统完成。[ERA：Introduction to ETCS Braking Curves](https://www.era.europa.eu/system/files/2022-11/Introduction%20to%20ETCS%20braking%20curves.pdf)、[ERTMS/ETCS FRS](https://www.era.europa.eu/system/files/2023-01/sos1_index001_-_era_ertms_003204_v500.pdf)。移动闭塞研究中的铁路可变限速也用于抑制到达瓶颈和速度扰动传播。[Li 等，2023](https://doi.org/10.1016/j.physa.2023.128895)

### 3.2 前车识别

只在以下条件同时成立时认定前后车关系：

1. 两车位于同一条实际有向路径或在预测窗内将进入同一冲突资源；
2. 前车的车尾沿该路径位于后车车头前方；
3. 两车之间没有会改变先后关系的未锁定分岔；
4. 位置数据在新鲜度阈值内。

可用间隔为：

`d_use = s_leader_rear - s_follower_front - d_fixed - d_uncertainty`

`d_uncertainty` 包括两次采样间车辆可能移动的距离、位置误差和执行延迟。数据过期时不得继续计算更高速度，只能保持更严格的旧限制、降级为基础设施限速，或在已确认安全的站前点请求停车。

### 3.3 安全速度

保守模式假设前车可以立即停止，不利用前车制动距离：

`v * tau + v^2 / (2 b_service) <= d_use`

解得：

`v_safe = -b_service * tau + sqrt((b_service * tau)^2 + 2 b_service d_use)`

其中 `tau` 是观测、计算、命令发布和原生 Hook 生效的总延迟上界，`b_service` 是计入坡度和车辆差异后、经过验证的保守有效减速度。`d_use <= 0` 或根号内数值无效时，结果直接钳制为零并进入停车/故障处理，不能继续发布非零限速。若以后能可靠得到前车速度和最差制动能力，可采用相对制动曲线，但不得直接假设前车会继续匀速。

最终命令速度为：

`v_cmd = min(v_safe, v_track, v_turnout, v_platform, v_timetable)`

必须增加：

- **滞回**：新速度与旧速度差小于阈值时不更新，避免来回抖动；
- **下降快、恢复慢**：安全边界降低立即下发，放宽需连续若干帧成立；
- **边界预瞄**：将限速发布到制动起点至风险区末端的实际有向边；
- **最小非零速度**：低于原生控制已验证范围时切换到官方停车命令，不能用近零限速冒充停车；
- **租约超时**：遥测或控制器失联后停止续租，回到游戏默认控制。

### 3.4 推荐周期

- 前车识别和安全包络：随高频列车位置帧更新，目标 0.5 秒左右；
- 原生限速租约刷新：1–2 秒；
- 远期 30–120 秒预测：每 2–5 秒更新。

如果只能获得当前约 2 秒的控制周期，则 `tau` 必须包含完整周期、遥测年龄和命令生效延迟，算法会更保守。

### 3.5 所需接口

当前 `SET_SPEED_LIMIT` 能承载非零租约，但还需要：实际有向路径、沿轨精确里程、车尾位置、边内范围和可信制动参数。缺少这些数据时，只能做拥堵缓解限速，不能把结果称为安全防护曲线。

## 4. 目标二：并行线路客货强制分配

### 4.1 算法选择

采用**时空网络上的容量约束最小费用流**。乘客使用按具体车次的动态分配；货物使用按货物类型区分的多商品流。研究表明，在拥挤公共交通中，容量约束必须落实到具体车次和剩余容量，满载造成的无法上车与后续排队也应进入模型。[Nuzzolo、Crisalli 与 Rosati，2012](https://doi.org/10.1016/j.trc.2011.02.007)、[Patzner 与 Müller-Hannemann，2024](https://doi.org/10.4230/OASIcs.ATMOS.2024.18)

### 4.2 决策变量与约束

对 OD 组 `q`、候选线路或车次 `r`、时间桶 `t`，定义分配量 `x[q,r,t]`。

基本约束：

- 流量守恒：`sum_r x[q,r,t] + deferred[q,t] = demand[q,t]`；
- 非负与整数约束；
- 每个车次每个区段的占用量不超过该区段剩余容量；
- 线路必须按相同方向服务同一 OD；
- 车辆必须支持该 cargo_id；
- 只重分配候车实体，不直接移动在车实体；
- 已进入最终登车窗口或刚被改派的实体在冷却期内冻结。

不能用“整条线路总容量减某个 OD 在车数”代替逐车次、逐区段容量，因为多个 OD 会在同一区段竞争同一容量。

### 4.3 目标函数

建议最小化：

`J = wait + travel + crowd + denied_boarding + transfer + reroute + instability + fairness`

具体含义：

- 等待时间和车内旅行时间；
- 拥挤惩罚，随载客率凸增长；
- 本次无法上车而递延到下一班的惩罚；
- 换乘次数和换乘失败风险；
- 改派成本，防止已经排队的实体被频繁搬动；
- 与上一周期分配的差异，抑制 L1/L2 间振荡；
- 最长等待或等待分位数，避免只优化总和而饿死少数 OD。

乘客可以先用广义成本形成目标比例，再通过有界命令逐步逼近；货物通常可直接按中央计划分配，但必须加入货物兼容性、交付期限和目标消费者约束。容量约束公共线路模型中的“无法上车概率”和动态排队，也可作为数据不足时的近似成本。[Schmöcker 等，2008](https://doi.org/10.1016/j.trb.2008.02.001)

### 4.4 在线执行

每 15–60 秒执行一次：

1. 用未来 5–15 分钟运行图生成车次—区段容量；
2. 删除方向、货物类型、目的地或容量证据不足的候选；
3. 解线性最小费用流；需要严格整数时，用整数最小费用流或小规模 MILP；
4. 只执行第一时间桶，且每个 OD 每周期最多移动 `min(固定上限, 当前候车量的一定比例)`；
5. 下一周期核对源/目标候车量、实际登车和实体数量守恒；
6. 收益低于阈值时保持现状。

这能处理“L1 爆满、L2 空闲”，同时避免简单平均分配。合理结果可能仍然偏向 L1，因为 L2 的等待、旅行时间或换乘成本更高。

### 4.5 当前接口缺口

`REASSIGN_OD` 已能承载有向乘客目标和数量，但还缺 cargo_id 原生过滤、逐实体去重、具体车次/区段容量账本，以及与单条命令关联的净迁移回执。货物控制在这些条件满足前应继续拒绝。

## 5. 目标三：站台和进站路线联合调度

### 5.1 算法选择

采用**替代图或析取资源模型上的滚动时域调度**。列车是作业，闭塞、咽喉进路和站台是一次只能被一个冲突动作占用的资源；同一列车的候选“进路＋站台”是替代方案。替代图最初用于带阻塞和无等待约束的作业车间问题，后来成为微观铁路冲突调度的常用表达。[Mascis 与 Pacciarelli，2002](https://doi.org/10.1016/S0377-2217(01)00338-1)

站台与进路必须联合选择。只选空闲站台可能把两列车同时导入同一咽喉；只给拥堵边加固定代价可能把列车导向即将被占用的平台。针对列车站台与重调度的研究也使用基于进路的混合整数模型，并以滚动时域算法降低在线计算量。[Lu 等，2022](https://doi.org/10.1016/j.tre.2022.102622)

### 5.2 候选动作

对每列接近车站且尚未锁定的列车，先由游戏或离线拓扑产生合法候选：

`option = (approach_route, platform, exit_route)`

候选必须满足：

- 方向和信号规则合法；
- 车辆能到达并离开；
- 站台长度明确足够；
- 站台支持该运输方式和停车方案；
- 与已经锁定的进路不冲突；
- 下游区间在预计发车时有容纳能力。

算法只在合法候选之间选择，不能自行构造游戏没有验证过的路径。

### 5.3 优化变量与约束

- 二元变量 `y[i,o]`：列车 `i` 是否选候选 `o`；
- 连续或离散变量 `T_enter/T_arrive/T_depart/T_release`；
- 对共享资源的先后变量 `z[i,j,r]`。

约束包括：每车恰选一个候选；同一资源的占用区间不得重叠；满足最小进路建立、运行、停车和释放时间；已锁定列车固定不变；站台占用覆盖整列到达至车尾清空；下游没有空间时不得把列车放入咽喉。

目标函数建议为：

`J = total_delay + max_delay + throat_occupation + platform_blocking + route_change + downstream_risk + starvation`

其中最长延误和等待年龄用于防饿死；改变已向列车发布但尚未锁定的方案要付稳定性成本。

### 5.4 求解与降级

- 预测窗：未来 3–10 分钟或接近车站的 10–30 列车；
- 每 2–5 秒滚动求解一次，只提交下一列或未来 10–20 秒内将锁定的动作；
- 主求解器可用 CP-SAT 或 MILP；
- 超时后使用“最早可行进入＋最早释放资源＋等待年龄加权”的确定性启发式；
- 已锁定进路、正在占用资源和安全限制永不被优化器撤销；
- 计划版本变化时，只取消本控制器拥有且尚未消费的租约。

### 5.5 命令映射

- `ASSIGN_PLATFORM` 表达选中的站台；
- `SET_PATH_COST` 对非选中或发生冲突的候选边施加有限期代价；
- 如果所有候选当前不可行，在站前安全等待点使用官方扣停/停车；
- 下一帧以实际锁定站台、实际走行边和资源释放时刻验证，不能用 Hook 全局命中次数代替。

## 6. 三个算法如何协调

采用共享的资源价格和预约表，而不是让三个求解器相互直接改命令：

1. 站场调度给未来资源时段生成预计等待和拥堵价格；
2. 客货分配把这些价格加入线路广义成本，减少向预计拥堵的线路继续导流；
3. 客货分配给出各车次预计上下车量和停车时间；
4. 站场调度据此更新站台占用和释放时刻；
5. 速度层读取已承诺的资源进入时刻，生成既满足安全间隔又尽量准时到达的速度上限；
6. 安全层可以覆盖任何上层计划，上层不得覆盖安全层。

每个主周期最多交换一到两轮预测，随后提交近期动作。没有必要在每周期求到全局最优；可行、稳定、能验证的滚动解比易超时的理论最优解更重要。

## 7. 实现顺序

### 阶段 A：只读回放

1. 建立实际有向路径坐标和资源—时间预约表；
2. 用历史帧离线运行三个算法，不发布命令；
3. 检查每个决策是否只使用当时可获得的数据；
4. 记录基线与算法结果：追停次数、总等待、P95 等待、吞吐、站外排队、进路变更次数。

### 阶段 B：影子运行

实时生成但不执行命令，比较游戏实际选择与算法选择。重点校准运行时间、制动延迟、站台释放和候车变化模型。

### 阶段 C：单问题闭环

依次启用：

1. 单车、单区段的非零限速；
2. 单站两条平行乘客线路的小批量改派；
3. 单站、两条合法站台进路的选择。

任何一项都必须有命令级后验验证和自动撤销，再进入联合控制。

### 阶段 D：联合滚动控制

先让客流分配读取站场拥堵价格，再让速度层跟踪站场预约时刻。货物改派应在 cargo_id 过滤、目的地和数量守恒完成后最后启用。

## 8. 结论

三个目标可以由一个统一的滚动时域框架协调，但不应由一个单体算法直接求解。推荐组合是：

- 区间限速：安全速度包络＋短时域速度预测；
- 客货分配：按具体车次和区段容量的动态最小费用流；
- 进站调度：站台—进路联合的替代图/析取资源调度；
- 全局协调：资源时间预约、拥堵价格、命令租约和后验验证。

现有项目已经有承载三类决策的基本命令接口。开始实现算法前，最高优先级仍是实际有向路径、逐车次容量、cargo_id 过滤、站场冲突资源和逐命令回执；这些数据决定算法是在优化真实系统，还是只在优化一个过度简化的影子模型。
